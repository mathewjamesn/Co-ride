3. Hosting and solution layout

3.1 Runtime and plan

  • .NET isolated worker model on .NET 10. Do not start on .NET 8 (support ends November 2026). Verify .NET 10 is offered on Consumption in the chosen region.
  • Windows Consumption plan. Microsoft has announced retirement of Linux Consumption; verify the current announcement before creating resources.
  • Publish with ReadyToRun. Register singletons once at start-up: CosmosClient, TableServiceClient, BlobServiceClient, IHttpClientFactory, Firebase app, OSRM client, config cache.
  • System-assigned managed identity for Cosmos (data-plane RBAC), Tables, Blobs and Queues. Third-party secrets through Key Vault references.
  • Timeouts: default 5 minutes. Nothing on the request path should exceed a few seconds; slow work goes to queues.

3.2 Warm-up timer

The existing "Wake Me Up" timer runs every 8 minutes in each Function App. It must do real work, not just return:

[Function("WakeMeUp")]
public async Task Run([TimerTrigger("0 */8 * * * *")] TimerInfo t)
{
    await _config.RefreshAsync();   // reload Config table into memory
    await _cosmos.WarmAsync();      // open connections
    await _tables.PingAsync();      // touch Users and Config tables
    await _jwt.PrimeKeysAsync();    // load signing keys
}

It keeps one instance warm. A burst of traffic that makes Azure add instances will still cold-start those. If that becomes a problem, move to Flex Consumption with always-ready instances (a plan change, not a code change).

3.3 OSRM access

OSRM runs on Azure Container Apps with public ingress protected by a key. The key lives in Key Vault and is sent as a header by a typed OsrmClient (HttpClient factory). Every OSRM call has a 1.5 second timeout and a circuit breaker (Polly); on failure the engine uses the Haversine fallback described in section 8. Keep minimum replicas at 1. Verify that both the car and foot profiles are built; the foot profile is needed for walking distance.

5. Login, JWT and blocking

Login is SMS OTP; the API then issues a signed JWT valid for one year, and every call checks the user's status and tokenVersion.

  1. POST /auth/otp/send then POST /auth/otp/verify. OTP is hashed, valid 5 minutes, max 5 attempts, rate-limited per phone.
  2. On success the API creates or loads the user and returns a JWT. Claims: sub (userId), ver (tokenVersion), iat, exp (1 year). Header carries kid.
  3. The app stores it in the Android Keystore (react-native-keychain) and sends Authorization: Bearer <token>.
  4. A Functions middleware validates signature, expiry, then loads the user row (cached in memory for 60 seconds) and checks status == Active and ver == tokenVersion. Any failure returns 401 {"code":"AUTH_REQUIRED"}; the app clears the token and opens login.
  5. Open endpoints (no token): /health, /config, /auth/*, /wallet/webhook (PhonePe signature check instead).

Blocking and logout:

  • Admin "block user" sets status = Blocked and increments tokenVersion. Effective within 60 seconds.
  • "Log out everywhere" (user or admin) increments tokenVersion.
  • Key rotation: keep two signing keys in Key Vault, selected by kid, so rotating never logs everyone out.

Verification (managed from Admin):

  • Org email OTP; endorsement by two verified users; personal ID photos uploaded to Blob via short-lived write-only SAS, reviewed in the Admin queue.
  • The verified flag is enforced server-side on offer, request and join, not only in the UI.
  • Store only a masked ID number (last 4 digits). Never store a full Aadhaar number.

6. Cosmos DB: the rides container

One container rides holds every ride document; documents are told apart by a type field. It lives in a serverless Cosmos account, because matching and nearby-place searches are spatial and come in bursts; serverless bills only for RUs used. The free-tier provisioned account is reserved for live location (section 6A).

Container settings:

  • Partition key path /pk. Value {city}|{yyyy-MM-dd} (IST departure date), for example KOC|2026-11-16. Trip-scoped docs use T|{tripId}.
  • Default TTL on (-1), each document sets its own ttl.
  • Indexing: spatial index on /routeSearch/?, /origin/?, /destination/? and /via/[]/? (Point and LineString). Exclude /routeFull/?, /cumTimeSec/*, /matches/* from indexing to save RU on writes.
  • One serverless account per subscription. It also holds a places container (preset places, hospitals and other points of interest) with a spatial index, for nearby-place searches.

6.1 Document types

type pk id Holds ttl
offer KOC|2026-11-16 KOC20261116-<ulid> driver, vehicle, seats, departure, fare/km, points, simplified route, full polyline, cumulative times, rules 2 days
request KOC|2026-11-16 KOC20261116-<ulid> rider, origin, destination, time window, seats, status, top-N matches[] 2 days
hold same as the offer hold-<offerId>-<requestId> seat hold while a rider decides 75 s (config)
live T|<tripId> live not used: live location is in the location account (section 6A) 1 day
crumb T|<tripId> timestamp sampled breadcrumb for share-trip and safety 7 days

The id carries city and date, so PkFromId("KOC20261116-...") returns KOC|2026-11-16. The client only ever holds the id, and every "open this offer or request" call is a point read (about 1 RU per KB). A search window that crosses midnight queries two partitions. Recurring offers are materialised nightly by a timer into one offer per date sharing a seriesId.

6.4 Hold and seat concurrency

  • Selecting an offer creates a hold doc (ttl from config, 75 s). Available seats = seatsTotal - seatsTaken - activeHolds.
  • Driver accepts (or auto-accept) → update the offer's seatsTaken with IfMatch on its ETag. On 412 Precondition Failed, reload and re-check. Delete the hold.
  • Hold and offer share a partition, so a transactional batch can create the hold and patch the offer together where needed.

6A. Live location: free-tier provisioned Cosmos account

Live driver location goes in its own Cosmos account on the free tier (1000 RU/s, provisioned), written and read directly by the apps with resource tokens, with no API call per update. This is the pattern already proven in the TOK app.

Container driverLocation:

  • Partition key /id, where id = driverId. One small document per driver, about 300 bytes.
  • Indexing mode none. Only point reads by id are used, so no index is needed and every write costs fewer RUs.
  • Dedicated throughput 1000 RU/s (the free-tier grant).
{
  "id": "u_8f2a91",
  "tripId": "T_01JC9A4K2B",
  "lat": 10.0021, "lon": 76.3004,
  "heading": 205, "speedKmh": 32,
  "ts": "2026-11-16T08:47:10+05:30",
  "seq": 412
}

Writes (driver app):

  • GET /location/token (API) returns a resource token scoped to that driver's one document, valid about 1 hour; the app refreshes it before expiry.
  • The app sends a Patch (set /lat, /lon, /heading, /speedKmh, /ts, /seq) only during an active trip, and only when the driver has moved 50 m or 15 s have passed.
  • On 429 the app skips that tick and sends the next one; no retry storm.

Reads (rider app):

  • When a trip starts, the API issues the rider a read-only resource token for the driver's document, valid for the trip.
  • The rider's map does a point read (about 1 RU) at the configured interval (polling.liveLocationSec).
  • The API reads the same document for SOS, share-trip and Admin.

Rules:

  • No authority flags in this document. Approval, verification, block status and trip permissions stay in Table Storage and the rides account, written only by the API, because a write token lets the driver change anything in his own document.
  • Tokens are issued only to active, verified users with an active trip; blocking a user stops new tokens.
  • Breadcrumbs for share-trip and safety are sampled by the API (for example once a minute) into the crumb documents, not written by the phone.

Capacity and cost:

  • About 5 RU per write and 1 RU per read: 1000 RU/s covers roughly 2,000 drivers sending every 10 seconds, and more with the movement rule. 5,000 simultaneous drivers is a later-scale target; when approached, raise throughput (paid above the free grant) or lengthen the interval.
  • Egress: small documents and point reads; Azure's first 100 GB of outbound data per month is free across all services.

8. Matching engine (full specification)

Cosmos does the rough cut by location; C# does the precise snapping, timing, fare and score. One HTTP function, no Durable Functions on the search path. This section supersedes the QuickRide Matching Engine Design 1.0 document.

8.1 At offer creation (done once per offer)

  1. The driver picks a route from Google Routes alternatives (section 9). The API holds the chosen route for 15 minutes by routeId; POST /offers references it, so a client cannot upload an invented route.
  2. Decode the polyline to WGS84 coordinates (lon, lat).
  3. Build cumTimeSec: preferred source is Google's per-step durations from the chosen route, spread over each step's vertices by length. Fallback: call OSRM route (car) with the same origin, via points and destination, annotations=duration, and accumulate segment durations onto the vertices by length ratio.
  4. Build routeSearch with Douglas-Peucker (DouglasPeuckerSimplifier, about 20 m tolerance in the metric CRS, converted back to WGS84). Validate with IsValid.
  5. Compute the overall bearingDeg (origin to destination).
  6. Write the offer document (section 6.2).

8.2 Coordinate system

  • Store everything in WGS84 (EPSG:4326), GeoJSON order [lon, lat].
  • For maths, project to UTM zone 43N (EPSG:32643) for Kochi; it is metric and accurate to well under 0.1%. Do not use Web Mercator (it inflates distances by about 1.5% at Kochi).
  • Keep a per-city CRS in a small CityProfile (code, name, UTM EPSG, timezone). Create the ProjNet transforms once as singletons.

8.3 Search pipeline (rider searching offers)

# Stage Where Notes
1 Candidate query Cosmos Single partition city|date. Parameterised (QueryDefinition.WithParameter). Filters: type = 'offer', status = 'OPEN', departAt within window (minus max ride time), seatsTotal - seatsTaken >= @seats, ST_DISTANCE(c.routeSearch, @origin) <= @r AND ST_DISTANCE(c.routeSearch, @dest) <= @r. Project only the fields needed. Cap at maxCandidates (100). Do not use TOP 10: Cosmos cannot rank by match quality.
2 Loose bearing cut C# Drop offers whose overall bearing differs from the rider's by more than looseBearingDeg (90). Cheap, removes only clearly opposite routes.
3 Decode and project C# Decode routeFull, project to UTM. Cache per offer id in memory (offers are immutable).
4 Snap pickup C# Closest point on the full route to the rider origin (DistanceOp / LengthIndexedLine.Project). Gives boardAlongM and straight-line boardOffsetM.
5 Snap drop after pickup C# Closest point to the rider destination searched only on the part of the route after boardAlongM (ExtractLine(boardAlongM, length), then project, then add boardAlongM). Prevents wrong snaps on looping routes.
6 Direction check C# If dropAlongM - boardAlongM is below a minimum (for example 300 m), reject. Never swap the indexes.
7 Segment bearing C# Bearing of the route segment between board and drop vs. the rider's origin-to-destination bearing. Reject above segmentBearingDeg (45).
8 Coverage C# coverage = rideM / riderDirectM where rideM = dropAlongM - boardAlongM and riderDirectM is the straight-line origin-destination distance. Reject below minCoverage (0.6).
9 Timing C# Interpolate boardAt and dropAt from cumTimeSec at boardAlongM and dropAlongM, plus departAt. Reject if boardAt is outside the rider window plus maxWaitMin.
10 Fare C# fare = round(rideM / 1000 * farePerKm * fareMultiplier, 1). Ride distance is along the driver's actual route. Do not use OSRM for this.
11 Pre-score, keep top 2N C# Score with straight-line walk distances (8.4).
12 Walking distance OSRM One OSRM table call, foot profile: sources = rider origin and the drop points, destinations = the board points and rider destination (or two calls: origin → boards, drops → destination). Replace straight-line walk with real walk metres. On timeout or open circuit: straight-line × 1.3 and walkSource = "estimate".
13 Final score, keep top N C# Re-score with real walking, drop walks above maxWalkM, keep keepTopN (20).
14 Write request Cosmos Upsert the request doc with matches[].

Target latency: under 800 ms for 100 candidates (stages 2 to 11 are about 1 ms per candidate once routes are cached).

8.4 Match score

walk     = 1 - clamp((walkToBoardM + walkFromDropM) / maxWalkM)
wait     = 1 - clamp(|boardAt - riderPreferredTime| in minutes / maxWaitMin)
expected = rideM / 1000 * referenceRatePerKm
fare     = 1 - clamp(|fare - expected| / expected)
bearing  = (cos(segmentBearingDiff) + 1) / 2
coverage = clamp(rideM / riderDirectM)

score = w.walk*walk + w.wait*wait + w.fare*fare + w.bearing*bearing + w.coverage*coverage
match% = round(100 * score)        // clamp() limits to 0..1; weights from api config, sum to 1
  • riderPreferredTime = windowFrom unless the rider sets a preferred time.
  • referenceRatePerKm is the city's typical rate per km, from config; tune it from real data.
  • Weights are tunable per city in the Config table; document every change in the audit log.

8.5 Reverse direction (driver seeing ride takers)

Same engine, reversed query. For a given offer, query type = 'request', status = 'SEARCHING', same partition and time window, with ST_DISTANCE(c.origin, @routeSearch) <= @r and ST_DISTANCE(c.destination, @routeSearch) <= @r, the offer's simplified line passed as a parameter. Then stages 2 to 13 per request, against this one offer. When a new offer is created, run this once and send FCM "new matching riders" to the driver; optionally add the offer into those requests' matches[].

8.6 Plan B if the spatial query costs too many RU

At offer creation, store cells: the geohash-6 cells (about 1.2 km × 0.6 km) the route passes through. Query with ARRAY_CONTAINS(c.cells, @originCell) for the rider's origin cell and its 8 neighbours, plus the same for the destination, then run the C# stages. Only adopt this after load testing shows the ST_DISTANCE query is too expensive.

8.7 Resilience

  • OSRM calls: 1.5 s timeout, Polly circuit breaker, straight-line fallback. Matching must never fail because OSRM is down.
  • Cache decoded and projected routes in memory per offer id (MemoryCache, sliding 30 minutes).
  • Validate all incoming geometry (lat/lon ranges, at least 2 points, ST_ISVALID on stored lines).

Route picker flow: POST /routes → up to 3 alternatives drawn on the map → tap to select → POST /offers with routeId. Add waypoint: centre pin from the map camera, reverse-geocoded, appended to via list (max from config).

10. Trips, chat and notifications

The server owns the trip state machine. Each action is a POST that checks who may perform it and writes the new state with an ETag.

States: SCHEDULED → STARTED → AT_PICKUP → ON_BOARD → AT_DROP → COMPLETED, plus CANCELLED from any state before COMPLETED. Per-rider sub-state in TripRiders (waiting, picked up, dropped, no-show).

FCM (HTTP v1 via Firebase Admin SDK for .NET), always sent from a queue so HTTP responses never wait on FCM:

Event Message Android channel
New chat message notification + data (type=chat, threadId) chat
Request or join accepted notification + data (type=accepted) accepted
Trip started, arrived, ended, cancelled notification + data trip
New matching riders, verification result notification + data general
  • Tones play when the app is closed because sound is a property of the Android channel, created at app start in the existing native module. Channel sounds cannot change after creation: choose final sounds before first release. Android 13+ needs the notification permission prompt.
  • Remove device tokens FCM reports as invalid.
  • Chat: save to ChatMessages, then FCM. On open or reconnect the chat screen fetches messages newer than its last id, so a missed push loses nothing.
  • Live driver location is not sent by FCM. The driver app patches its own location document directly in Cosmos (section 6A), only during an active trip, when moved 50 m or every 15 s (foreground service with location type, Android 14 rule); no API call. The old live doc is not used; the rider's map point-reads the driver's location document with a read-only resource token, instead of polling GET /trips/{id}/live at the configured interval.

11. Wallet and payments (PhonePe PG v2)

Top-up credits the wallet once, server-verified; ride payment is reserved at booking and settled by an idempotent queue job.

Top-up:

  1. POST /wallet/topup {amount} → check min/max from config → PaymentOrders row CREATED with unique merchantOrderId + PaymentIndex row → PhonePe OAuth token (cached until expiry) → PhonePe create order → return orderId and token.
  2. The app opens PhonePe checkout with the React Native SDK.
  3. On return the app calls GET /wallet/topup/{id}; the server asks PhonePe for status. The app's own result is never trusted.
  4. Webhook POST /wallet/webhook: verify PhonePe's authorization header, find the user via PaymentIndex, confirm via status API.
  5. Credit once: in one Wallet-partition batch, add ledger row L|reverse-ts|topup-<orderId> and update balance with ETag; then mark the order CREDITED. A duplicate ledger RowKey means already credited, so stop.
  6. Timer re-checks orders stuck in CREATED/PENDING at 5, 15 and 60 minutes; marks failed after 24 hours. Refunds via PhonePe refund API plus a reversing ledger row.

Ride payment:

  • At booking: reserve the fare: ledger row reserve-<tripId>-<riderId> and reserved amount on the balance row, in one batch. Booking is refused if available balance (balance minus reserved) is too low.
  • At trip end: enqueue settle {tripId}. The handler runs three idempotent steps, each keyed by tripId so retries skip work already done: debit rider (release reserve, ledger ride-<tripId>), credit driver (ledger earn-<tripId>-<riderId>, minus commission from config), mark trip settled.
  • Cancellation rules release or partially capture the reserve (rules to be confirmed).
  • Staging uses PhonePe sandbox, production live credentials, each from that subscription's Key Vault. Driver payouts are a separate future design.
